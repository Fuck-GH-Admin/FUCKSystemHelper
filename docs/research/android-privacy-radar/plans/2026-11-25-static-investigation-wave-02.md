## 1. 本轮目标

本轮不再泛泛扩展权限清单，也不提前安排用户进行本地实机测试。目标是把上轮遗留的四条链尽可能闭合：

1. VDR 请求中的坐标字段从哪里来、在哪些条件下被写入、是否进入真实请求构造路径。
2. `ll_pre`、`cl_pre`、`wf_pre` 的生产、持久化、消费、上传和清理生命周期。
3. Java/JNI 边界的真实输入输出、native 库实现范围，以及哪些行为不能仅凭 Java 包装层推断。
4. `intime.dat` 的生产、格式、调度、上传、响应处理、失败重试和清理生命周期。

最终产物必须回答“数据源 → 采集条件 → 转换/缓存 → 请求构造 → 网络发送 → 响应/删除”的完整链路，并明确哪些节点仍然缺少证据。

## 2. 调查工作流

### Track A — VDR 坐标来源与请求分派

**核心问题**

- `a.a.a.b.d.a(double,double)` 的全部调用点在哪里？
- 坐标参数来自 Baidu LocationListener、GNSS 回调、缓存恢复、配置响应，还是其他来源？
- 字段写入后是否被序列化进 `qt=vdr` 请求？是否存在坐标有效性、时间戳或权限 gate？
- `a.a.a.b.w` 中 executor 相关字段的所有写入点和读取点是什么？VDR/config 请求分别走哪个重载？
- `kahts` 对应的 N 值到底控制哪些请求入口？不能把不同重载或进程混为一谈。

**预期检查对象**

- `decompiled/jadx/sources/a/a/a/b/d.java`
- `decompiled/jadx/sources/a/a/a/b/w.java`
- `decompiled/jadx/sources/a/a/a/b/a.java`
- `decompiled/jadx/sources/a/a/a/b/c.java`
- `decompiled/jadx/sources/a/a/a/i/g.java`
- 相关 Smali、DEX xref 和所有调用方。

**交付要求**

- 坐标字段写入点矩阵：调用方、参数来源、触发条件、字段效果。
- 请求分派图：请求类型、方法重载、executor/线程、TLS 分支、进程。
- 没有 xref 或调用证据的字段不得标记为“已上传”。

### Track B — ll_pre / cl_pre / wf_pre 历史数据生命周期

**核心问题**

- 三类数据各自代表什么？名称只能作为线索，不作为语义证据。
- 数据由哪个回调、系统 API 或缓存生产？
- 是否包含 BSSID/SSID、Cell ID、经纬度、时间戳或其他标识符？
- 数据保存在哪里、保留多久、是否去重、是否有上限？
- 哪个请求读取这些数据？字段如何编码？什么条件下发送？
- 成功、失败、超时、关闭开关、配置切换时分别如何清理？
- 是否存在跨进程读写或共享文件路径？

**预期检查对象**

- `decompiled/jadx/sources/a/a/a/b/f.java`
- 全部引用该类字段/方法的 Java 文件与 Smali。
- SharedPreferences、SQLite、文件读写和 JSON/二进制序列化的交叉引用。
- Manifest 中相关 Service/Receiver/Provider 的进程与权限声明。

**交付要求**

- 每种数据分别绘制 producer → storage → consumer → request → cleanup。
- 逐字段记录敏感性、来源、精度、保留期；未知项写 UNKNOWN。
- 区分“读取过”“缓存过”“加入请求”“已发出请求”，不能跨级推断。

### Track C — JNI/native 边界

**核心问题**

- Java native 声明与 JNI 导出符号如何一一对应？
- `Jni.a`、`Jni.b` 的参数、返回值、异常和调用方是什么？
- native 库是否参与压缩、加解密、签名、设备标识生成、环境检测或协议封装？
- 相关算法是否能从二进制、符号、字符串、反汇编、交叉引用中复核？
- 是否有不同 ABI 的实现差异或缺失库？
- 哪些 Java 层声称的“完整性保护”实际仅覆盖部分字段？

**预期检查对象**

- `decompiled/jadx/sources` 中所有 native method 声明及其调用方。
- `decompiled/apktool/lib/`、APK 原始 ZIP 中的 .so、ELF headers、符号表、字符串和 JNI_OnLoad。
- 反编译/反汇编产物（若仓库已有）；如缺工具或二进制未归档，明确列出缺口。
- 不把 JNI 方法名、字符串命中或单一 ABI 的符号直接当作算法结论。

**交付要求**

- native 方法清单：类/方法/签名/ABI/导出符号/调用点/输入输出/证据。
- 算法结论分为已还原、部分还原、仅有线索、不可见。
- 对无法静态还原的部分，明确未来需要什么真实样本或动态证据；本轮不执行动态实验。

### Track D — intime.dat / VDR 文件与上传生命周期

**核心问题**

- `intime.dat` 由谁创建、写入、追加、截断和删除？
- 文件是否包含位置、轨迹、惯导、时间戳、传感器或设备标识？
- `vdrtt`、`vdrconfig_gz`、VDR 上传线程分别承担什么职责？
- 上传触发条件、文件大小门槛、分片/压缩/加密方式和服务端响应处理是什么？
- 失败后保留、重试、覆盖还是丢弃？是否可能与下次上传竞争？
- 是否有不同版本/配置开关改变文件格式或上传路径？

**预期检查对象**

- `decompiled/jadx/sources/a/a/a/b/j.java`
- `decompiled/jadx/sources/a/a/a/b/d.java`
- `decompiled/jadx/sources/a/a/a/b/x.java`
- `decompiled/jadx/sources/a/a/a/i/g.java`
- 全仓库 `intime.dat`、`vdrtt`、`vdrconfig_gz`、文件操作、压缩/加密和响应码交叉引用。

**交付要求**

- 文件状态机：不存在 → 创建/追加 → 封存 → 上传 → 成功/失败 → 删除/保留/重试。
- 对数据格式只写能由解析器、写入代码或二进制证据支持的字段。
- 对上传成功、服务端持久化等事实保持 UNKNOWN，除非存在真实服务端证据。

## 3. 主调查者的交叉验证与整合职责

四条工作流的发现必须经过统一复核，不允许把分支调查者的初步结论直接合并为最终结论。主调查者需要：

1. 回到原始 Java、Smali、DEX xref 和 ELF 证据逐项复核。
2. 对关键调用链至少核对生产者、调用点和消费者三个方向；有条件时同时核对 Java 与 Smali。
3. 为每个结论记录仓库路径、行号/方法签名、代码基线和对应证据片段。
4. 排查反编译器误还原、混淆重名、重载误配、跨进程静态状态误判和不同请求路径误合并。
5. 对互相矛盾的证据保留分歧，不强行统一。
6. 将已有报告中的过宽表述标注为修订，不悄悄覆盖历史结论。
7. 报告写完后重新读取 GitHub 文件、检查 commit diff 和研究分支 HEAD。

## 4. 证据等级与术语

| 等级 | 定义 | 可以使用的措辞 |
|---|---|---|
| E0 | 命名、字符串、第三方文档、相似版本线索 | 候选、线索、待核实 |
| E1 | 当前样本静态代码、Smali、DEX xref、ELF 静态证据 | 代码显示、静态调用链表明 |
| E2 | 本样本真实设备/模拟器运行时观察，有可复核日志/文件/调用栈 | 在指定环境观察到 |
| E3 | 本样本真实网络请求/响应/抓包或服务端证据 | 实际请求/响应显示 |
| E4 | 多设备/多版本复现或独立证据交叉验证 | 在指定范围内可复现 |

特别区分：
- 代码组装了请求 ≠ 网络请求已经发出。
- 网络请求发出 ≠ 服务端已接收或持久化。
- 本地读取到标识符 ≠ 标识符一定成功上传。
- 服务器返回配置 ≠ 配置对应行为已经执行。
- native 声明存在 ≠ native 算法已还原。

## 5. 本轮禁止事项与范围边界

- 不登录用户 QQ/运营商账户，不触碰用户实体手机，不要求用户进行实机操作。
- 不对生产上游发起请求，不发送伪造设备注册，不抓取或重放真实用户流量。
- 不建立模拟服务器、伪造回包或模拟设备来替代真实服务器证据。
- 不执行可能改变设备状态、清除数据、触发注册或上传的动态实验。
- 不把第三方 SDK 的一般行为直接归因于 SystemHelper 样本。
- 不修改 `main`、原始 APK、原始反编译产物或既有证据文件。
- 只向本研究分支的 `docs/research/android-privacy-radar/` 写入计划、调查记录和报告。

## 6. 并行协作说明

当前可用的 GitHub/工作区工具没有提供可直接派发独立代码逆向子代理的接口。因此本轮不虚构“已派出子代理”。实际执行将按 Track A–D 并行检索和分批核查，主调查者负责统一证据标准、去重、冲突审查和最终报告。若后续出现真正可用的独立子代理执行接口，再将四条工作流拆分给子代理，并要求其提交带路径/行号的证据清单，而非仅交摘要。

## 7. 完成标准

只有满足以下条件才宣布本轮静态调查完成：

- 四条链均有完整的已知节点图，缺失节点明确标为 UNKNOWN。
- 所有关键结论都有可复核路径、行号/方法签名和证据片段。
- 所有请求路径明确区分请求构造、发送调用、响应处理和服务端未知状态。
- Java/JNI/Smali/ELF 的边界与证据缺口明确。
- 至少完成一次反证搜索：主动寻找能推翻初步结论的调用点、分支条件、异常路径和清理逻辑。
- 形成正式报告和更新后的 RUN-LEDGER 记录。
- 对 main、APK 和原始逆向证据的未修改状态进行复核。

## 8. 执行顺序

1. 固定本计划（本文件）。
2. 并行执行 Track A–D 的全仓库搜索与调用关系收集。
3. 对每条关键链回读源文件上下文，核对 Smali/DEX/ELF。
4. 做交叉反证与冲突消解。
5. 编写一份综合报告；必要时按主题拆分附件，但必须有统一索引。
6. 更新 RUN-LEDGER，验证提交和分支状态。
7. 只有静态链闭合后，才讨论未来实机验证所需的最小、安全、可复核步骤；本轮不要求用户执行。
