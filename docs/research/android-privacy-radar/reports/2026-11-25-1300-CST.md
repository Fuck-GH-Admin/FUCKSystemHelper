# Android 高权限组件与隐私控制：导出触发面、SignalInfo 数据结构与配置控制链

- 时间：2026-11-25 13:00 CST
- 样本代码基线：`main` / `fe7b5b66d6f82168f99d95af98259de2e9deeb81`
- 研究分支：`research/KEEP-android-privilege-privacy-radar`
- 本报告性质：静态代码与 Smali 复核；新增观察均为 E1（代码证据），不代表设备上已经执行或服务器已经收到
- 本轮没有进行实体设备、模拟器、真实服务器、抓包或网络请求测试；这些项目全部 NOT_RUN

## 0. 本轮结论

本轮没有升级此前 H01–H08 的运行时证据等级，但新增了几条此前没有完整闭合的静态链：

1. **导出的 OnBootReceiver 不只处理开机广播。** 任何非 BOOT_COMPLETED / QUICKBOOT_POWERON 的 Action（包括内部 PendingIntent 使用的 null Action）都会进入另一条分支，注册监听并触发 RegType=F/B。该 Receiver 在 Manifest 中 exported=true，且没有组件级 permission。Android 官方文档明确说明显式 Intent 会直接送达指定组件，不受其 intent-filter 限制。
2. **RegisterHelperService 是无组件权限保护的 Binder 控制面。** 它允许修改注册服务器地址、批量修改七组采集/注册间隔、开关日志和删除偏好文件。Manifest 虽定义了 signature 级自定义 permission，但没有把它配置到该 Service；Binder Stub 只检查 interface descriptor，没有调用方 UID/权限校验。
3. **SignalInfo 的数据结构比此前报告列出的更具体。** 采集记录可包含 IMEI、ICCID、IMSI、MNC、TAC、CID/NCI、PCI、LTE/NR 频段和信号质量指标，以及经纬度/海拔。代码中 IMEI 不做掩码；IMSI/ICCID 的掩码规则反而对四个被识别为联通的前缀（46001/46006/46009/46010）跳过。
4. **SignalInfo 是周期采样、批量上传。** GetSignalInfoReceiver 默认每 30 分钟由精确 Alarm 唤醒；SignalInfoRegisterReceiver 默认每 12 小时加随机初始偏移触发 RegType=R。每次有效位置回调可按双 SIM 生成两条记录。
5. **失败重试并非可靠队列。** 当前注册失败会写入 dmregister；但历史重试线程取出记录时先删除再发送，发送失败没有重新入队。队列最多保留 11 条，且只在一次新的注册成功后尝试处理一条。
6. **Baidu SDK 另有本地开发 URL 覆盖文件。** 服务启动时读取 app-specific external files 下的 baiduLocDev/loc_local_config，可覆盖 cfgs、loc 等端点；校验只检查 owner 字符串和 URL 中是否包含 “https”，没有主机 allowlist 或签名验证。文件是否能被其他应用写入仍未知。
7. **修正 kahts/TLS 的适用范围。** kahts 来自 qt=vdr 的 VDR 配置缓存，不是 gnmcon/gnmcrm 所在的 qt=conf 配置对象。它只影响网络基类的 a(String) 入口；Baidu 服务在 :remote 进程中运行，其全局 SSL 默认工厂不会跨进程影响 SystemHelper 自有注册线程。

## 1. 导出组件与外部触发面

### 1.1 OnBootReceiver 的非开机分支可触发 F/B

证据：

- `decompiled/apktool/AndroidManifest.xml`：OnBootReceiver 声明 `android:exported="true"`，intent-filter 只有 BOOT_COMPLETED 和 QUICKBOOT_POWERON，没有 `android:permission`。
- `decompiled/jadx/sources/com/mobiletools/systemhelper/control/OnBootReceiver.java`：只有两个开机 Action 进入开机初始化分支；其他 Action 直接进入 SIM/网络监听器初始化和设备注册分支。
- `decompiled/apktool/smali/com/mobiletools/systemhelper/control/OnBootReceiver.smali`：非开机分支调用 n.c()、n.a(context)，随后读取 firstPowerOn，选择 RegType=F 或 RegType=B。
- `decompiled/apktool/smali/c/d/a/a/n.smali`：F/B/S/T/R 分支最终汇入统一 Thread.start 路径；此前 0032 报告已纠正 JADX 对线程启动位置的误判，本轮复核没有推翻该结论。

内部设计本身解释了这个分支为什么存在：BOOT_COMPLETED 分支会通过显式 PendingIntent，在 240000 ms（4 分钟）后再次启动 OnBootReceiver；该 Intent 没有 Action，因此会进入非开机分支并触发首次 F/B 注册。

安全含义：由于 Receiver exported=true、没有组件级权限、代码又不验证非开机 Action，外部应用可以尝试通过显式 Intent 触发同一分支。Android 文档说明显式 Intent 会直接投递给指定组件，不受 intent-filter 限制；本 Manifest 未声明 receiver 的 intentMatchingFlags/enforceIntentFilter。参考：
- https://developer.android.com/guide/components/intents-filters
- https://developer.android.com/guide/topics/manifest/receiver-element

这证明的是一个**静态可达的本地触发入口**，不是已经完成的第三方应用实机触发实验。实际是否启动上报仍受 d.e、系统权限、网络和设备信息条件限制。

### 1.2 SIMStateReceiver 也存在非 SIM Action 的 T 检查路径

- Manifest 中 SIMStateReceiver 同样 exported=true，没有组件级 permission。
- Smali 中，若 Action 为 SIM_STATE_CHANGED，则按 SIM 状态处理；若 Action 为 null 或其他值，则进入后续设备识别分支，并调用 RegType=T。
- RegType=T 在 n.smali 中有额外条件：只有 SIM 信息与已保存状态比较后确认发生变化，才继续创建并启动线程。因此这条入口比 OnBootReceiver 的 F/B 路径更受限。
- 内部 SIM ready 延迟 PendingIntent 同样使用无 Action 的显式 Intent。日志字符串写“6 minutes”，但 Smali 常量是 180000 ms，即 3 分钟；这是日志与实际延迟不一致。

ConnectStateReceiver 虽然也 exported=true，但当前检查到的代码主要记录连接状态，不是本轮发现的主要数据上传入口。

## 2. RegisterHelperService：无组件权限的 Binder 控制面

### 2.1 Manifest 与 Binder Stub

- Manifest 定义了 `com.mobiletools.systemhelper.permission`，protectionLevel=signature。
- 但 RegisterHelperService 声明只有 exported=true，没有 android:permission。
- `RegisterHelperService.onBind()` 无条件返回 Binder Stub。
- `service/a.java` 的 onTransact 对每个业务事务调用 enforceInterface 检查接口描述符；没有 getCallingUid、checkCallingPermission 或包名/签名校验。

因此，signature permission 的定义本身并没有保护这个 Service。

### 2.2 五个 Binder 操作

| 事务 | 代码行为 | 影响 |
|---|---|---|
| a(String) | 写入 SharedPreferences 的 serverAddress | 改变后续注册/历史补传目标地址 |
| a(int) | 修改七组周期参数 | 改变 Schedule、AppInfo、SignalInfo、GetSignalInfo 的间隔 |
| a(boolean) | 修改 d.f1331a 并保存 preference_enable_log | 开启或关闭日志 |
| a() | 读取 preference_enable_log | 查询日志状态 |
| b() | 删除固定路径的 SharedPreferences XML | 清除 serverAddress 和周期偏好等持久设置 |

a(int) 的映射为：
- scheduleInterval = i
- appInfoInterval = 8i/5
- scheduleInterval2、appInfoInterval2、signalInfoInterval2 = 4i/5
- signalInfoInterval = 6i/5
- GetsignalInfoInterval = 3i/5

没有发现对 i 的上下界检查。该方法只写偏好值，没有直接重建所有现存 PendingIntent；新值会在后续调度代码重新读取时生效。

默认值来自 `c/d/a/b/d.java`：
- Schedule：24 小时
- AppInfo：24 小时
- SignalInfo：12 小时
- GetSignalInfo：30 分钟
- 三个首次调度偏移量分别随机取 0–24 小时

### 2.3 与导出 Receiver 组合后的控制链

静态调用链可以串起来：

`RegisterHelperService Binder` → 写 serverAddress/周期偏好 → `OnBootReceiver` 非开机分支 → RegType=F/B → RegisterThread → `l.h(context)` 读取 serverAddress → HttpHelper 发起 POST。

默认 serverAddress 是 `http://dm.wo.com.cn:18080/register`；d.f1332b 默认 false，因此正常路径读取 SharedPreferences 中的 serverAddress。setter 没有 URL allowlist 或 scheme 校验。HttpHelper 只接受以 http:// 或 https:// 开头的地址；Manifest 的 usesCleartextTraffic=true。

重要限制：注册 JSON 主体仍经过 AES 加密，AES key 派生信息再经硬编码 RSA 公钥加密后放入 sign 参数。因此，任意本地应用改变目的地址，不等于它能直接解密上传主体。能确认的影响是目的端可被改写、明文 URL 元数据（model/manuf/sign）可被目的端看到，以及注册流程可能被重定向或破坏；不能据此声称攻击者获得了明文 IMEI/IMSI。

## 3. SignalInfo：周期位置采样与蜂窝无线数据

### 3.1 调度链

- OnBootReceiver 开机分支通过 AlarmHelper 设置 GetSignalInfoReceiver 的首次延迟，默认 GetsignalInfoInterval=1800000 ms。
- GetSignalInfoReceiver 在处理时会先重新安排下一次 Alarm，再判断是否允许开始定位；因此关闭采集 gate 时仍会周期唤醒并重新检查，但不会因此证明发生了定位或上传。
- SignalInfoRegisterReceiver 通过 AlarmHelper 按 signalInfoInterval2 + signalInfoInterval 安排首次执行；默认随机偏移 0–24 小时 + 12 小时，之后按 12 小时周期执行。
- AlarmHelper 使用 setExactAndAllowWhileIdle，Alarm 类型参数为 2。

### 3.2 Baidu LocationClient 与隐私 gate

GetSignalInfoReceiver 在构造 LocationClient 前调用 `com.baidu.location.h.b(true)`。Baidu LocationClient 的构造路径会检查静态隐私许可布尔值 K；此处由宿主代码主动置 true，再创建客户端。这是宿主对 Baidu SDK 自身 consent guard 的程序化放行，不应等同于用户明确同意。

SystemHelper 自身另有 d.e gate：
- vivo：device_provisioned=1 且 Settings.Secure 的 operator_service_improve_plan=1；
- 非 vivo：当前代码只检查 device_provisioned=1，没有检查同一个 operator_service_improve_plan。
- Android 运行时权限和系统特权仍然影响 TelephonyManager/LocationClient 实际能否返回数据。

定位选项设置包括 BD09LL 坐标类型、Hight_Accuracy 模式和 scanSpan=0。代码按一次 Alarm 触发 LocationClient，回调成功后读取经度、纬度、海拔字段。

### 3.3 单条 SignalInfo 的字段

GetSignalInfoReceiver 在每个有效定位回调中，分别检查 SIM slot 1/2 的 subscription ID；大于 0 时分别调用 control.d 读取该 slot 数据，并可能写入两条记录。

control.d 在 d.e 为 true 时读取：
- IMEI：普通设备调用 getImei；Xiaomi 分支反射调用 getImeiForSlot；
- ICCID：getSimSerialNumber；
- IMSI：getSubscriberId；
- SIM MNC、当前 network operator；
- LTE/NR 的 TAC、CID/NCI、PCI、频段、带宽、NRARFCN；
- LTE/NR 信号指标：RSRP、RSRQ、SINR、CQI table index、CQI；
- 网络类型及通话/数据失败相关字段。

SignalInfo JSON serializer 明确包含 IMEI、ICCID、IMSI、MNC、TAC、CID、PCI、NetworkType、ARFCN、Bands、Bandwidth、CQI、RSRP、RSRQ、SINR、CallDisconnectCause、DataFailCause、EPSFallback、LONGITUDE、LATITUDE、ALTITUDE、SPEED、BEARING 等键。不是每个可选字段都能从本次回调确认有值；序列化前还要求 IMEI、MNC、IMSI、TAC、CID、PCI、NetworkType、network operator 等必需字段非空。

记录入库还有一层严格条件：network operator 必须以 460 开头，且对应 SIM slot subscription ID 大于 0。

### 3.4 标识符掩码规则

control.d 的代码逻辑：
- IMEI 直接写入 nVar.f1344b；本路径未发现对 IMEI 做掩码。
- ICCID/IMSI 只有在满足长度条件且 `l.b(IMSI)` 为 false 时才执行掩码。
- l.b 将 46001、46006、46009、46010 识别为联通前缀并返回 true；因此这些前缀跳过掩码。
- 对其他满足长度条件的运营商，IMSI 保留前 10 位并追加 *****；ICCID 保留前 10 位并追加 **********。
- 若平台 API 返回空值，代码会使用 ex01 占位；此时不会获得原始完整标识符。

所以准确表述是：**代码没有统一匿名化策略；IMEI 不掩码，联通前缀的 IMSI/ICCID 不掩码，其他运营商的 IMSI/ICCID 才按条件截断。** 实际是否取得完整值仍取决于 ROM、权限授予和 TelephonyManager 返回值。

### 3.5 SignalInfo 缓存与 R 上传

- 数据库文件名 signalhelper，表 signal。
- 插入前检查记录数；达到 100 条时删除查询结果中的第一条再插入。查询没有显式 ORDER BY，因此不能仅凭 SQL 保证被删的一定是最旧记录。
- RegType=R 从 signal 表读取 JSON 数组，放入注册对象的 P 字段，然后清空 signal 表，再启动上传线程。
- 若 RegisterThread 因网络条件或 HTTP 失败返回 false，正常失败路径会把完整注册对象（包括 P 数组）写入 systemhelper 数据库的 dmregister 表。因此“先清空 signal 表”本身不等于必然丢失；是否能转存还依赖后续线程和 d.e 状态。

## 4. dmregister 历史队列：补传是 best-effort，不是可靠重试

### 4.1 写入与容量

RegisterThread 发送失败时，把当前注册对象 JSON 写入 systemhelper 数据库的 dmregister 表。插入前计算 iMax=max(0,count-10)，按 ID ASC 删除 iMax 条，再插入当前记录。由此队列稳定上限实际是 11 条，而不是严格 10 条。

### 4.2 读取/删除先于发送

HistoryPostThread 仅在一次新的注册成功后启动，并且每次只处理一条：
1. 查询 dmregister，不指定 ORDER BY；
2. 调用 moveToLast() 取一条；
3. 立即按 ID 删除；
4. 返回 JSONObject；
5. 再调用 HTTP helper 发送。

如果发送失败，没有重新插入该记录的逻辑。因此这不是“发送成功后确认删除”的可靠队列，而是先出队、后发送的 best-effort 补传。由于查询无 ORDER BY，moveToLast 也不能从 SQL 层面保证取到最旧记录；日志虽写 queryOldestRecord，但查询没有排序条件。

另外，成功解析 JSON 的 return 路径在 cursor/window close 之前提前返回，存在 Cursor/CursorWindow 未关闭的资源泄漏风险。

## 5. Baidu SDK：本地 URL 覆盖、VDR 配置与 TLS 开关

### 5.1 本地开发 URL 覆盖文件

Baidu 服务启动时，`a.a.a.h.a.a(Context)` 先调用 `a.a.a.b.b.a().a(context)`，再启动 Handler。该方法读取：

`getExternalFilesDir(Environment.DIRECTORY_MOVIES)/baiduLocDev/loc_local_config`

配置结构包含 url_config 数组，按 type 修改 cfgs、loc、vdr_log_update、hdyawupdate、basement_inout、indoor_roadnet、indoor_poi_data、indoor_rects 等 URL。

校验只检查：
- owner 不包含 default_owner；
- url 不等于 default_url；
- url 字符串中包含 “https”。

没有发现签名校验、owner allowlist 或 host allowlist；“包含 https”也不是严格的 scheme 校验。文件位于 app-specific external files，能否由其他应用写入取决于 Android 版本、存储隔离和具体 ROM；本轮没有验证其可写性。因此目前只定性为本地开发/调试端点覆盖能力，不把它说成普通应用可直接利用的入口。

### 5.2 kahts 的来源与生效时机

需要把两个使用同一 cfgs endpoint 的请求分开：

- `qt=conf`：此前追踪的 commcfgs 配置对象，包含 gnmcon/gnmcrm 等定位采集控制字段。
- `qt=vdr`：由 a.a.a.b.d 构造的 VDR 配置请求；请求参数包含 SDK 版本、im/cu 标识、型号、Android 版本、包名、city、locmode、locper；若对象的坐标字段已被写入，还会附加 x/y。当前尚未找到所有 a(double,double) 写入点，故不能声称 x/y 每次都会发送。

VDR 配置缓存 vdrconfig_gz 在 Baidu 服务启动时先被解码、解析；缺失或超过 24 小时时，延迟 5 秒刷新。收到带 data 的成功响应后，会先保存 vdrconfig_gz，再立即调用解析函数。kahts 在该 VDR JSON 解析器中写入 N 字段。

因此：
- 全新/无缓存状态下，N 默认 0；
- 已有缓存的安装会先采用缓存中的 kahts，再进行刷新；
- 不能把“默认 N=0”泛化成所有设备、所有启动状态；
- kahts 与 gnmcon/gnmcrm 不是同一个配置字段或同一个 JSON 对象。

### 5.3 TLS 开关的真实范围与进程边界

a.a.a.i.g 的 a(String) 入口根据 VDR 配置的 N 选择网络实现：
- N != 1：进入 legacy HttpsURLConnection 路径，使用自定义 TrustManager；其 checkServerTrusted 只检查证书有效期，没有建立正常 CA 信任链；配套 HostnameVerifier 只比较 URL host 与传入 host 字符串，没有检查 SSLSession 中的证书身份。
- N == 1：进入 OkHttp 路径；当前静态代码未发现为该路径安装同一自定义 TrustManager。
- 其他重载入口并不都经过这个 N 分支；例如 executor overload 和显式弱 TLS 的入口需要分别看调用方，不能把 kahts 描述成全局、全请求开关。
- VDR intime.dat 上传类另有显式弱 TLS 设置，不由 kahts 单独控制。

Manifest 声明 com.baidu.location.f 服务运行在 `:remote` 进程；Smali 中该 Service 委托给 a.a.a.h.a。SystemHelper 自有 RegisterHelperService/OnBootReceiver/RegisterThread 没有声明独立 process，运行在应用默认进程。因此 Baidu :remote 中调用 HttpsURLConnection.setDefaultSSLSocketFactory 的全局效果是进程内的，不会自动影响默认进程中的 SystemHelper 注册 HttpHelper。这修正了“整个应用进程都被同一弱 TLS 工厂影响”的过宽表述。

## 6. 另一个边界问题：China MNC 检查是 fail-open

SystemHelper 主注册线程通过 `l.a(bVar)` 检查 MNC：
- 如果已读到非占位且非 460 开头的 MNC，会返回 false；
- 如果 MNC 为空、ex00、ex01，或数据槽字段缺失，则可能继续返回 true；
- 捕获异常时也返回 true。

因此主注册路径不是严格 fail-closed 的“中国网络限定”。当 MNC 信息不可用或解析异常时，代码会倾向于放行；Wi-Fi 条件满足时可能继续尝试注册。SignalInfo 入库路径不同，它直接要求 network operator 以 460 开头。两条路径的地域门控不能混为一谈。
