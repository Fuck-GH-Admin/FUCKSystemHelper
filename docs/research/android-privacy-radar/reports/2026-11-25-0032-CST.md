- 证据等级：**E1（仓库内原始 APK 反编译 / Smali / DEX xref 静态证据）**

## 1. 关键纠错：RegType=R 的 SignalInfo 上报线程确实会 start()

此前基于 JADX 的 `c.d.a.a.n.a(Context,String)` 输出，曾误判 `R` 分支只构造 `RegisterThread` / IP 收集线程而未执行 `Thread.start()`。

回查原始 Smali：

- `decompiled/apktool/smali/c/d/a/a/n.smali`
- 方法 `a(Landroid/content/Context;Ljava/lang/String;)Lcom/mobiletools/systemhelper/control/b;`

可以看到 `A/R/B/F/S/T` 的相关分支最终均跳到统一的 `:goto_0`，然后调用 `Ljava/lang/Thread;->start()V`。

### R 分支真实静态路径

1. 构建设备对象并写入 `RegType="R"`。
2. 打开 `signalhelper` SQLite。
3. 读取 SignalInfo JSONArray。
4. 数组非空时写入 `deviceInfo.P`。
5. 调用数据库清理，再关闭 DB。
6. 若 `GlobalSetting.getIPAddress && isUserPermissionOpen`，构造 `control.c` 获取 IPv6；否则直接构造 `control.g`。
7. 两条路径最终都执行 `Thread.start()`。
8. `control.c` 完成 IPv6 读取后继续启动 `control.g`。
9. `control.g` 对 DeviceInfo JSON 加工后向注册服务器发送；网络失败时会落入 `dmregister` 本地重试库。

因此，**“R 分支未启动上传线程”结论撤销**。静态证据支持：只要前置门控满足且 SignalInfo DB 非空，R 分支存在完整的主机自有上报执行链。

## 2. SystemHelper 自有上报链：入口、门控、数据和重试

### 2.1 默认目的地与可变服务器地址

`c.d.a.b.d.l` 默认服务器为：

`http://dm.wo.com.cn:18080/register`

实际发送时由 `c.d.a.b.l.h(Context)` 读取 `serverAddress` SharedPreferences；因此运行期目的地可被本地配置覆盖。

### 2.2 发送线程

`com.mobiletools.systemhelper.control.g`：

- 仅在 `GlobalSetting.isUserPermissionOpen` 为真时执行发送；
- 序列化 `deviceInfo.a()`；
- 生成签名参数和 AES 加密正文；
- 通过 POST 发送；
- HTTP 200 / 416 被视为可接受结果；
- 发送失败时把完整待发送数据写入 `dmregister` SQLite，后续由历史重试线程处理。

### 2.3 注册对象包含的设备字段

`com.mobiletools.systemhelper.control.b.a()` 的 JSON 至少包括：

- Manuf / Model / HWVersion / SWVersion / OS / OSVersion；
- 双卡 IMEI / ICCID / IMSI / MNC；
- NetworkType / TAC / CID / PCI；
- VoLTE / 5G / VoNR 状态；
- DataSlot / AccType / IPv6 / SubType / DeviceType；
- RegType / SpecVersion=5.0 / ClientVersion / Time；
- SigInfo 数组；
- AppInfo 数组。

是否能够获得每项真实值取决于系统版本、授予权限、OEM 特权和运行条件。

### 2.4 中国网络与用户设置门控

`c.d.a.b.l.a(deviceInfo)` 对 MNC 做 460 前缀检查；异常时为 fail-open（返回 true）。

`GetSignalInfoReceiver` 的用户门控：

- vivo：`device_provisioned == 1` 且 `Settings.Secure["operator_service_improve_plan"] == 1`；
- 非 vivo：只检查 `device_provisioned == 1`。

因此本样本在 vivo 分支上存在明确的“运营商服务改进计划”设置门控；不能无条件声称定位/SignalInfo 路径在用户关闭该设置后仍启动。

## 3. Alarm 调度闭环

`c.d.a.b.a` 使用 `AlarmManager.setExactAndAllowWhileIdle`：

- AppInfo：默认主周期 24h，首次附加随机偏移；
- Schedule：默认主周期 24h，首次附加随机偏移；
- SignalInfo 上报：默认主周期 12h，首次附加随机偏移；
- GetSignalInfo：默认 30min，并在 Receiver 中自调度下一次；
- SIM 状态检查另有延迟调度。

对应 Receiver：

- `AppInfoRegisterReceiver` -> RegType `A`
- `SignalInfoRegisterReceiver` -> `R`
- `ScheduleRegisterReceiver` -> `S`
- `SIMStateReceiver` -> 条件下 `T`
- `OnBootReceiver` -> 初始化/周期注册 `B/F`

这说明主机自身的设备注册、应用统计和 SignalInfo 并不是孤立 helper，而有持久调度入口。

## 4. Baidu BDLocConfigManager：远程配置链已闭合

关键类：`a.a.a.b.a`（BDLocConfigManager）。

### 4.1 默认值

构造器默认：

- 配置刷新间隔：`freq = 300s`
- `gnmcon = 0`
- `gnmcrm ≈ -0.1`
- `lpcs = 1`
- `iupl = 1`

即原始 GNSS 导航电文采集默认关闭。

### 4.2 配置请求

内部网络类向：

`https://loc.map.baidu.com/cfgs/loc/commcfgs`

发送：

- `qt=conf`
- `req=Jni.b(...)`

成功响应只要求能解析成 JSON，然后压缩/Base64 保存至 SharedPreferences 的 `BDLocConfigManager_newConfig`。未发现响应签名或 MAC 校验。

下一次配置管理器初始化时：

1. 读取 `_newConfig`；
2. Base64 解码；
3. 解压；
4. 调用 `a(String)` 解析并写入运行配置。

### 4.3 有效 GNSS 控制字段

解析器明确写入：

- `gnmcrm` -> 配置对象 `h`
- `gnmcon` -> 配置对象 `i`
- `lpcs` -> `g`
- `iupl` -> `j`

客户端 `com.baidu.location.h.b()` 将这些值打入 Binder Bundle：

- `gnmcrm`
- `gnmcon`
- `lpcs`
- `iupl`

服务端 `a.a.a.b.c$b` 接收后：

- 若 `gnmcon == 1`，设置全局 `a.a.a.i.i.u0 = 1`；
- 若 `gnmcrm > 当前 t0`，更新全局采样概率 `t0`；
- `lpcs` 等同步进入全局运行状态。

## 5. 远程配置 -> 原始 GNSS 导航消息 -> locnu 上传

`a.a.a.g.d.k()` 启动 GPS/GNSS 监听时存在条件：

`u0 == 1 && new Random().nextDouble() < t0`

满足后创建并注册 `GnssNavigationMessage.Callback`。

回调：

`onGnssNavigationMessageReceived()`
-> `z.f().a(gnssNavigationMessage, gpsTime)`
-> Handler case 11
-> `x.b().a(GnssNavigationMessage, gps_time)`

`a.a.a.b.s` 解析并聚合导航电文原始字节/子帧；`a.a.a.b.x` 在短窗口内整理记录后，使用 AES/CBC helper 加密 `info` / `enl`，请求：

`https://ofloc.map.baidu.com/locnu`

因此静态证据已经闭合：

**commcfgs 远程配置 -> gnmcon/gnmcrm -> Binder 配置同步 -> 注册 GnssNavigationMessage.Callback -> 原始导航电文处理 -> locnu 网络请求。**

边界：

- 默认配置是关闭的；
- 没有动态证据证明真实服务器当前返回 `gnmcon=1`；
- 真实设备是否满足 API/权限/硬件条件仍为 NOT_RUN；
- 不能把这一能力写成“设备已经上传原始 GNSS 数据”。

## 6. commcfgs 配置完整性风险：默认路径使用宽松 TLS

网络基类 `a.a.a.i.g.a(String)` 根据 `a.a.a.b.d.i().N`（由 `kahts` 控制）选择实现：

- 默认 `N != 1`：启动内部 `e` Thread；
- `N == 1`：走 `a.a.a.b.q` OkHttp。

默认路径中的内部 `e`：

- 调用 `HttpsURLConnection.setDefaultSSLSocketFactory(a.a.a.i.i.g())`；
- 使用 `C0021g(URL)` 作为 HostnameVerifier。

`a.a.a.i.i.g()` 的 X509TrustManager：

- `checkServerTrusted()` 只对证书执行 `checkValidity()`；
- 不建立 CA 信任链；
- `getAcceptedIssuers()` 返回空数组。

HostnameVerifier：

`return url.getHost().equals(str);`

这并未根据对端证书验证主机身份。

由于 BDLocConfigManager 的 `commcfgs` 请求通过继承的 `a(url)` 发出，且默认 `N=0`，**首次/默认配置获取落入该宽松 TLS 路径**。

同时配置响应未见应用层签名验证。因此静态上存在“配置完整性受未可信网络影响”的安全边界：一旦响应被替换，客户端会保存合法 JSON 并在后续初始化中解析，包括 `gnmcon/gnmcrm` 等敏感采集开关。

这仍是静态风险分析；本报告未执行 MITM，也不证明现实网络已发生篡改。

## 7. 网络基类并非所有请求都使用同一 TLS

需区分：

- `a(String)` 默认 -> 宽松 TLS Thread；
- `a(executor,String)` -> 另一 Runnable，未显式安装宽松 TrustManager，依赖默认 OkHttp/HttpsURLConnection 信任；
- `a(executor,boolean,String)` -> 另一执行路径；
- `a(boolean,String)` -> 宽松 TLS Thread；
- `N==1` 的 `q` -> 普通 OkHttpClient，代码中未配置自定义 TrustManager/HostnameVerifier。

因此不能笼统写“Baidu SDK 所有 HTTPS 都失效”。需要按具体调用入口分级。

## 8. VDR 轨迹上传仍是明确的宽松 TLS 路径

`a.a.a.b.j` 将 `baidu/tempdata/intime.dat` 作为 multipart 字段 `location_dat` 上传到：

`https://itsdata.map.baidu.com/long-conn-gps/sdk.php`

该函数明确：

- 设置上述宽松默认 SSLSocketFactory；
- 设置同类 HostnameVerifier；
- POST 二进制轨迹文件；
- 只检查 HTTP response code。

因此该独立轨迹上传函数本身具有明确的服务端身份认证缺陷，不依赖网络基类的 fallback 判断。

## 9. 三个 JADX 失败的回包处理器已用 Smali 重建

### 9.1 `a.a.a.b.h$c.a(boolean)`

- 支持响应 JSON 中的 `enc` 字段并 AES 解密；
- 构造 Baidu location 对象；
- 处理 code 161 成功定位；
- 根据客户端坐标类型调整结果；
- 写入首次地址缓存；
- 回调给调用方；
- 失败映射到错误码。

### 9.2 `a.a.a.b.l$a.a(boolean)`

该路径是当前 Wi-Fi AP 的 hotspot 分类缓存，不应与“已保存 Wi-Fi 列表上报”混为一谈：

- 可解密 `enc`；
- 读取 `content.imo.mac` / `mv`；
- 将返回的 mac 与当前 BSSID 的 Murmur/hash 标识核对；
- 更新 SQLite `hstdata(id,hst,tt)`；
- 将 hotspot 分类通过 Bundle 返回。

### 9.3 `a.a.a.b.m$c.a(boolean)`

主 `bloc` 定位响应：

- 可解密 `enc`；
- 读取 `content.net_loc_save`；
- 构造 location 对象；
- code 161 时可进入 hotspot/history 保存逻辑；
- 把结果发送给 Handler `what=21`；
- 网络失败进入 `what=63`。

这说明 Baidu 主定位请求不仅“发数据”，服务端响应还参与本地定位结果、缓存和控制流。

## 10. 已保存 Wi-Fi SSID/关联次数路径

`a.a.a.c.f`：

- 调用 `WifiManager.getConfiguredNetworks()`；
- 读取 `WifiConfiguration.SSID`；
- 反射读取 `numAssociation`；
- 仅保留关联次数 > 0 的项；
- 构造 `qt=cltrw`、`cltr[0]=Jni.e(JSON)`；
- 服务端响应保存到 `wcnf.dat`；
- 响应可设置 `ison` 和 `cfg.frq`；
- 默认周期 24h。

`a.a.a.b.d` 另有有效配置字段：

- `upload_ssid_switch`
- `single_ssid_length_max`
- `max_request_ssid_number`

但该配置类的约 196 个 JSON key 中，很多只是 `optInt/optDouble/get...` 后丢弃；不能把“出现字段名”当成“有效远程控制”。

## 11. 导出的 Binder 控制面

Manifest：

- 定义了 signature 权限 `com.mobiletools.systemhelper.permission`；
- 但 `RegisterHelperService` 本身 `android:exported="true"`，没有声明该 permission。

Binder stub `com.mobiletools.systemhelper.service.a.AbstractBinderC0057a.onTransact()`：

- 只做 `Parcel.enforceInterface()`；
- 未见调用者 UID、签名或自定义权限校验。

接口提供：

1. 设置 `serverAddress`；
2. 批量修改采集/上报时间间隔；
3. 删除 SystemHelper 自身 SharedPreferences 文件；
4. 设置日志开关；
5. 查询日志开关。

`enforceInterface` 只是 Binder interface token 一致性检查，不构成调用者身份认证。

因此静态上存在一个高价值的本地 IPC 验证点：普通第三方应用在真实 ROM 上是否能够 bind 并调用这些 transaction。**本轮 NOT_RUN。**

## 13. 本地最小验证建议（仅人工、NOT_RUN）

优先顺序：

1. **不改网络、不做 MITM**：先观察真实设备上 `operator_service_improve_plan` 开/关与 GetSignalInfoReceiver / Baidu LocationClient 是否启动。
2. 记录 `commcfgs` 真实响应中是否存在 `gnmcon` / `gnmcrm`，并核对缓存 `BDLocConfigManager_newConfig`；只做被动抓取/日志核验。
3. 若真实配置启用了 `gnmcon`，观察是否注册 `GnssNavigationMessage.Callback`，以及是否出现 `ofloc.map.baidu.com/locnu` 连接。
4. 观察 `signalhelper` -> RegType=R -> `dm.wo.com.cn:18080/register` 的真实出站；记录失败时是否转存 `dmregister`。
5. 用自有测试 APK 在授权设备上验证 `RegisterHelperService` 是否可由普通 UID 绑定；先调用只读日志状态 transaction，再决定是否进行可回滚写操作。
6. TLS 缺陷的动态验证单独隔离，不与真实账号/真实位置数据混用；优先使用测试网络和无敏感数据环境。

## 14. 仍未闭合的问题

- `commcfgs` 在真实服务器当前版本具体返回哪些开关；
- `kahts` 是否在真实环境切换到 OkHttp 正常 TLS 路径；
- 宽松全局 `setDefaultSSLSocketFactory` 调用后，进程内后续其他 HttpsURLConnection 的实际影响顺序；
- VDR/indoor/CLTR 各自真实触发率与服务器响应；
- vivo 系统镜像实际授予此 APK 的 signature/privileged 权限、AppOps 与 SELinux 上下文；
- exported Binder 在目标 ROM 的实际可绑定性及系统层附加限制；
- 后端真实接收、保存、关联和生命周期策略。

## 结论

本轮最重要的变化不是增加更多“可疑 API 清单”，而是把几个关键静态问题从“能力存在”推进到了“调用链闭合”：

1. 修正 R/SignalInfo 上报线程的错误判断；
2. 闭合主机自己的 SignalInfo 周期采集 -> SQLite -> R 上报 -> 失败重试；
3. 闭合 Baidu commcfgs -> GNSS 原始导航电文回调 -> locnu 上传；
4. 证明该敏感配置链默认落在宽松 TLS 实现上；
5. 用 Smali 恢复三个 JADX 失败的网络回包控制流；
6. 确认 exported Binder 对服务器地址和周期存在无组件权限的本地控制面。

这些均为 E1 静态证据；真实设备执行、网络收包和后端使用仍需独立动态验证。
