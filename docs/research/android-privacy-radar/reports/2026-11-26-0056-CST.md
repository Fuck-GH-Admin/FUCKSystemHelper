## 2. Track B 复核：cl_pre / wf_pre / ll_pre 的真实控制流

### 2.1 存储容器与上限

a.a.a.b.f：

- 使用 MapCoreServicePregck SharedPreferences；
- cl_pre、wf_pre、ll_pre 均以 Base64 文本保存；
- 内存中使用 Deque；
- f=5、g=5，因此可见代码会把三类历史控制在最多约 5 条；
- cl_pre / wf_pre 使用三字段记录的差分编码；
- ll_pre 使用七字段记录的差分编码。

Base64 是可逆编码，不是加密。

### 2.2 q()/t() 的语义已经由对象自身输出确认

com.baidu.location.c.toString() 明确输出：

- lat = q()
- lon = t()
- altitude = d()
- speed = B()
- time = D()

因此 f.java 中：

- cVar.t() = longitude；
- cVar.q() = latitude。

这不再只依赖变量名或外部 SDK 经验判断。

### 2.3 cl_pre 的写入条件

f.a(cVar, str, Location) 的静态控制流：

- cVar != null；
- str 必须等于 gcj02；
- locType cVar.r() 必须为 61 或 161；
- source 字符串 cVar.v() 包含 cl；
- h == 1。

满足后写入：

longitude, latitude, normalized-time

随后调用持久化方法，最终写入 cl_pre。

### 2.4 ll_pre 的写入条件和字段

ll_pre 并不是普通三字段坐标历史。

在以下分支写入：

- source 不走 wf 快速分支；
- source 不满足 cl 分支；
- locType == 61；
- i == 1；
- Android Location 参数非 null。

可见七字段为：

1. cVar.A() —— 当前仍保留 getter 原名，语义未完全确认；
2. (int)cVar.z()；
3. cVar.d() —— altitude；
4. normalized cVar.C()；
5. cVar.B() —— speed；
6. Android Location.getLongitude()；
7. Android Location.getLatitude()。

后续记录相对首条做逐字段差分，其中经纬度差乘 10^6 后转为整数。

### 2.5 wf_pre 的名称不能被当成严格来源标签

这是本轮最需要明确写下的语义修正。

f.java 的实际控制流中，在 locType 61/161、gcj02 条件成立后，wf_pre 对应的 deque 写入语句位于前述 cl/ll 分支之后：

this.d.offerFirst(cVar.t() + "," + cVar.q() + "," + normalized-time)

因此当前静态代码支持的准确说法是：

- wf_pre 保存三字段位置历史；
- source 包含 wf 时当然会走到这里；
- 但从可见控制流看，这个写入并不被一个严格的 source == wf 条件包围；
- 因此不能把 wf_pre 简化描述成“只保存 Wi-Fi 定位历史”。

后续报告应继续使用“wf_pre 历史队列”这个代码名称，而不是替它赋予严格的 Wi-Fi-only 语义。

## 3. Track D 复核：intime.dat 从 Location 入口到上传线程

### 3.1 生产入口已可连成完整静态链

新增核对得到：

a.a.a.b.z 的 Handler message 1：

1. 从 Bundle 取出 Parcelable Location；
2. 调用 j.k().e(location)。

j.e(Location)：

1. 首次调用会执行 h() 初始化配置；
2. 检查远端/本地配置中的 on、bash、net、tcon 等条件；
3. 满足条件后通过 Handler post Runnable；
4. Runnable 调用 j.c(location)。

j.c(Location)：

1. 调用 d(location) 写入轨迹 buffer；
2. 调用 a() 检查是否达到封存/上传条件。

j.a() 满足条件后：

1. 将 F 列表转成 byte[]；
2. 创建 baidu/tempdata/intime.dat；
3. 若旧文件存在，先 delete；
4. 写入完整 byte[]；
5. new b().start()。

线程 b.run()：

- 调用 a(file, "https://itsdata.map.baidu.com/long-conn-gps/sdk.php")。

因此目前可以静态闭合：

Location → z Handler → j.e → j.c → j.d → 内存轨迹 F → intime.dat → multipart POST

这比单独找到上传函数更强：生产者、buffer、文件、上传线程已经连通。

### 4.3 与 GNSS/离线定位的邻接关系

同一上传线程管理器 z.java 还承担：

- message 1 → intime.dat 位置入口；
- message 2/3 → y.a(...)；
- message 4 → 周期调度并调用 x.b().a()；
- message 11 → GnssNavigationMessage → x。

因此 y、x、j 并非完全孤立模块，而是由同一个 LocUploadThreadManager 调度的多条数据路径。
