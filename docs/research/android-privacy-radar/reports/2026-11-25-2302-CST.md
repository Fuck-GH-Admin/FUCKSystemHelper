## 0. 核心结论

本轮闭合了 VDR 坐标配置请求的一段关键调用链，并发现远端配置字段 kahts 会影响 SDK 公共网络基类的请求分派方式。

**最重要的纠正：目前确认的 qt=vdr 请求是向 Baidu 获取 VDR 配置的请求，不是已经证明的 VDR 轨迹上传。**

已经确认：

1. 定位结果类型 61、161、66 会把 Baidu Location 结果中的纬度、经度和城市写入 VDR 配置管理器。
2. VDR 配置请求发往 https://loc.map.baidu.com/cfgs/loc/commcfgs，参数中包含 qt=vdr；若坐标满足代码条件，则将经度放入 x、纬度放入 y。
3. 请求还携带 SDK、CUID/IMEI 分支标识、设备型号、系统版本、包名、城市、定位模式及 ACCESS_FINE_LOCATION 权限状态。
4. VDR 配置在服务启动时先从本地缓存加载；没有缓存或缓存超过 24 小时才触发刷新，延迟 5 秒发送。
5. 响应 data 被存入 vdrconfig_gz，经 Base64 解码、GZIP 解压后解析为 JSON。
6. JSON 中的 kahts 被写入 d.N；公共网络基类 a.a.a.i.g 读取该值，决定走 HttpsURLConnection 直连线程路径还是 OkHttp 请求路径。
7. 两条路径的 TLS 实现不同：直连路径显式安装自定义 TrustManager（仅检查证书有效期），OkHttp 路径则使用未自定义 TLS 配置的 OkHttpClient。
8. 在扫描的 91 个 a.a.a Java 源文件和 39 个 Baidu Location / SystemHelper Java 源文件中，没有找到 w.f86a 或 w.f87b 的非空赋值；当前可见代码中的可选 ExecutorService 仍初始化为 null。反射、native 或扫描范围外的写入尚未完全排除。

## 1. VDR 坐标来源

### 1.1 写入点

a.a.a.b.c 的定位结果处理逻辑在满足以下条件时执行 VDR 状态更新：

- cVar 非 null；
- cVar.r() 等于 61、161 或 66。

随后执行两次调用：

- d.i().a(cVar.q(), cVar.t())；
- d.i().c(cVar.g())。

Baidu Location 对象的 toString 将 q() 标为 lat、t() 标为 lon。因此：

| 来源 | 含义 | 写入字段 |
|---|---|---|
| cVar.q() | 纬度 | d.n |
| cVar.t() | 经度 | d.o |
| cVar.g() | 城市字段 | d.l |

d.a(double,double) 本身只保存两个 double，不进行坐标转换。后续请求构造中，d.o 被放入 x，d.n 被放入 y。

### 1.2 请求参数

d.a() 构造的请求参数包括：

| 参数 | 来源/内容 |
|---|---|
| sdk | 固定 SDK 版本 9.521 |
| stp | 固定值 1 |
| cu 或 im | 根据 CUID 是否可用选择 |
| mb | Build.MODEL |
| abtest | 固定值 1 |
| fixa9 | 固定值 2 |
| sv | Android 版本字符串，最多截取 10 字符 |
| os | Android SDK_INT |
| pack | 应用包名 |
| city | 最近一次写入的城市字段 |
| locmode | 当前定位模式 |
| locper | ACCESS_FINE_LOCATION 权限状态 |
| x | 经度，仅当经纬度均大于约 0.1 时加入 |
| y | 纬度，仅当经纬度均大于约 0.1 时加入 |
| selftest | 固定值 0 |
| rpmmc | SDK_INT 大于 25 时加入，值为 0 |
| qt | vdr |

完整参数字符串被放入 it 字段。这里调用的是 Jni.a(String)，最终进入 native a(byte[], 132456)；它不是 n.java 中的 AES/CBC 加密函数，也不是 Jni.f 的 ee + tp=4 路径。

### 1.3 请求触发时机

服务启动处理函数依次执行：

1. d.i().b(false)：加载本地 vdrconfig_gz 缓存并解析；
2. d.i().h()：检查是否需要刷新。

h() 的逻辑：

- 如果本地 vdrconfig_gz 为空，触发刷新；
- 如果缓存非空，则比较上次时间与当前时间，超过 86,400,000 ms（24 小时）才刷新；
- 刷新前更新本地 vdrtt 时间戳；
- 使用 Handler.postDelayed 延迟 5,000 ms 执行请求 Runnable。

请求 Runnable 检查 Android API 版本大于等于 17 后，优先尝试 w.d().b() 返回的 ExecutorService；若为空，则走公共网络基类的 a(String) 分派逻辑。

因此，这条链是“定位结果更新坐标缓存 → 服务启动/过期触发 → 延迟请求配置”，不是每次定位回调都直接发送一次 qt=vdr。

## 2. VDR 配置响应与持久化

d.a(boolean) 在成功响应且 JSON 存在 data 时：

- 清空旧的 vdrconfig；
- 将 data 原字符串写入 vdrconfig_gz；
- 调用 b(true) 解析新配置。

b(true) 会读取 vdrconfig_gz，执行 Base64.decode，再调用 i.i.b(byte[])。i.i.b 使用 GZIPInputStream 解压，随后将解压内容解析为 JSON 并映射到 VDR 配置字段。

配置存储通过 r.a() 完成；该实例的主 SharedPreferences 名称为 MapCoreServicePreIA。与前一份报告中的 MapCoreServicePregck（历史定位队列）不是同一个 Preferences 文件。

远端配置的实际内容未在本轮取得；报告只记录客户端解析器明确支持的字段和控制流。

## 3. kahts：远端配置控制网络请求分派

### 3.1 赋值与默认值

d 类的构造函数将 N 初始化为 0。配置解析器遇到 kahts 字段时执行：

- 读取 JSON 的 kahts 整数值；
- 写入 this.N。

服务启动先加载缓存配置，再执行 h() 刷新。因此实际运行值可能来自本地缓存，而不一定是构造函数默认值 0。

### 3.2 公共网络基类的分支

a.a.a.i.g.a(String) 读取 d.i().N：

| 条件 | 分派路径 |
|---|---|
| N != 1 | 创建并启动独立 Thread e(str) |
| N == 1 且调用线程为主线程 | 创建 Thread d(str)，其 run() 调用 g.b(str) |
| N == 1 且调用线程不是主线程 | 直接调用 g.b(str) |

g.b(str) 最终调用 q.c().a(...)。

这不是单纯的线程池大小参数。它切换了网络实现路径：

### 3.3 N != 1：HttpsURLConnection 直连路径

Thread e.run() 中：

- 设置 HttpsURLConnection 的默认 SSLSocketFactory 为 i.i.g()；
- 创建 HttpsURLConnection；
- 执行 HTTPS POST；
- 设置请求头、超时和 HostnameVerifier；
- HostnameVerifier 比较 URL.getHost() 与传入 hostname 是否完全相等。

i.i.g() 创建的自定义 X509TrustManager 对服务端证书逐张调用 checkValidity()，但没有看到正常的 CA 链验证逻辑。也没有看到证书 pinning。

由于使用 HttpsURLConnection.setDefaultSSLSocketFactory，这是进程级默认设置；后续创建的 HttpsURLConnection 可能继承该默认工厂。实际影响范围仍需设备验证。

### 3.4 N == 1：OkHttp 路径

q 类在构造函数中创建 OkHttpClient：

- 使用默认 OkHttpClient.Builder；
- 只设置 connect/read/write timeout，均为 12,000 ms；
- 没有设置自定义 SSLSocketFactory；
- 没有设置自定义 HostnameVerifier；
- 使用 Request.Builder.url(...).post(...).build() 发起同步 execute()。

因此，从静态配置看，N=1 分支使用 OkHttp 的默认 TLS 配置；N!=1 分支使用 HttpsURLConnection 并显式安装有效期检查型 TrustManager。

这意味着 kahts 能改变 SDK 网络请求的 transport/TLS 实现路径。不能据此断言服务器当前实际下发了哪个值，也不能断言某次连接实际接受了何种证书。

## 4. ExecutorService 管理器的 xref

w 类包含两个公开字段：

- f86a：ExecutorService；
- f87b：ExecutorService。

构造函数将二者都置为 null。类内只有 getter 和 shutdown，没有创建线程池的代码。

在本轮扫描的 130 个应用/SDK Java 文件中：

- 找到了 d、l、m、x、y、c 等类读取 w.d().a()/b() 的调用；
- 找到了服务停止时 w.d().c() 的 shutdown 调用；
- 没有找到 f86a/f87b 的非空赋值。

因此，在目前可见 Java 路径中，如果不存在反射、JNI 或扫描范围外的写入，这些调用会走 executorService == null 的 fallback 分支，最终由 g.a(String) 根据 kahts 选择请求路径。

这是基于扫描范围的结论，不宣称已排除所有动态写入。

## 5. 与上一份报告的 TLS 发现如何拼接

上一份报告确认 intime.dat 上传函数直接调用 HttpsURLConnection.setDefaultSSLSocketFactory(i.i.g())。

本轮进一步发现，公共网络基类在 N!=1 时也会安装同一个自定义工厂。

因此目前至少有两处静态路径会显式使用该工厂：

1. intime.dat 文件上传；
2. a.a.a.i.g 的 N!=1 直连请求。

而 N==1 的 g 路径使用 OkHttp 默认 TLS 配置。

这使 kahts 与 TLS 验证方式之间建立了明确的静态联系。仍需强调：没有真实 TLS 握手证据，也没有观察到 MITM。
