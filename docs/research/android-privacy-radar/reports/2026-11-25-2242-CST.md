## 0. 结论摘要

本轮已把 Wave 02 中的 JNI/AES 边界推进到可逐字节复现，并补齐了几条与定位、GNSS 和 Wi-Fi 热点识别有关的数据路径。

最重要的结论：

1. ARM64 原生库中的 JNI 函数 Java_com_baidu_location_Jni_ldkaiv 会还原并返回一组固定的 16 字节 AES key 与 16 字节 IV。还原结果为 **qsHcaEWjX0j1dGmZ** 和 **1122334455667788**。
2. Java 层明确使用 **AES/CBC/PKCS5PADDING**。它既用于 GNSS 导航电文上报字段的加密，也用于解开部分定位/热点识别接口响应中的 enc 字段。
3. 不能把所有 Baidu 请求都称为 AES 加密：普通定位/热点请求中的 bloc 字段使用 Jni.f 的 native 编码；enc=2 是请求中附带的模式标记，响应 enc 字段才由 n 类的 AES 解密函数处理。GNSS locnu 路径则直接对 info 和 enl 两个字段调用 AES 加密。
4. cl_pre、wf_pre、ll_pre 三类历史记录保存在 SharedPreferences MapCoreServicePregck 中。它们使用 Base64 和差分编码，不是 AES 加密；当前静态调用链显示这些历史字段会被拼入 Wi-Fi 热点识别请求。
5. intime.dat 是单独的二进制位置轨迹文件，包含时间、经纬度、方向、速度及经过 XOR 混淆的应用/设备标识。代码通过 multipart/form-data 将它发送到 itsdata.map.baidu.com。
6. intime.dat 的上传路径调用自定义 X509TrustManager：服务端证书只做有效期检查，没有看到标准 CA 链验证；同一路径另有精确主机名比较。该结论是 TLS 实现的静态发现，不代表本轮观察到任何中间人攻击。
7. 上述证据只证明当前样本中存在这些代码路径和请求构造逻辑，不能证明它们在某台真实设备上已经执行，也不能证明服务器实际收到、保存或使用了数据。

## 1. JNI 隐藏常量：完整还原

### 1.1 Java 调用链

- Jni.java 的静态包装方法 a() 调用 native ldkaiv()，返回值可为 null。
- n.java 构造单例时调用 Jni.a()，要求返回字符串包含分隔符，并且 split 后恰好有两个元素；随后将两个元素保存为 f53b[0] 和 f53b[1]，并将 f52a 设为 true。
- 因此，密钥与 IV 并非 Java 源码中的明文常量，而是由 liblocSDK8b.so 的 native 函数返回。

### 1.2 ELF 证据

分析对象：

- 路径：extracted/lib/arm64-v8a/liblocSDK8b.so
- Git blob SHA：4c673c37ce9da9f39891f9dae333c63201ba55d6
- 文件大小：368,568 bytes
- 本仓库 extracted/lib 当前只列出 arm64-v8a；其他 ABI 的等价实现尚未在本档案中核对。

关键 ELF 信息：

| 项目 | 值 |
|---|---|
| JNI 导出符号 | Java_com_baidu_location_Jni_ldkaiv |
| 符号 VA | 0x21e00 |
| 符号大小 | 0x170 bytes |
| 常量所在节 | .rodata |
| 常量 VA | 0x142b0 |
| 本样本文件偏移 | 0x142b0 |
| 解码长度 | 34 bytes |

原始 34 字节：

~~~text
53506c4647627f43721b461c4a685d6b4e02050704040b0d0e0e090b080877797a43
~~~

反汇编确认 ldkaiv 调用了本地 XOR 辅助函数（VA 0x2453c），并将结果写入全局缓冲区（VA 0x3a660）；随后通过 JNI NewStringUTF 路径构造 Java 字符串。辅助函数逐字节执行：

~~~text
decoded[i] = encoded[i] XOR ((34 + i) & 0xff)
~~~

解码结果（末尾包含 NUL）：

~~~text
717348636145576a58306a3164476d5a7c3131323233333434353536363737383800
~~~

ASCII：

~~~text
qsHcaEWjX0j1dGmZ|1122334455667788
~~~

所以 n.java 实际拿到的两个字符串为：

| 用途 | 值 | ASCII 字节数 |
|---|---|---:|
| AES key | qsHcaEWjX0j1dGmZ | 16 |
| AES IV | 1122334455667788 | 16 |

这不是通过猜测变量名得到的值：常量 VA、原始字节、native XOR 循环、JNI 返回路径和 Java 消费者均已逐项对应。

### 1.3 加解密算法

n.java 使用：

- 算法：AES
- 模式：CBC
- Padding：PKCS5PADDING
- Key：上表中的 16 字节字符串
- IV：上表中的 16 字节字符串
- 输入/输出封装：Android Base64，flag 0

解密方法执行 Base64.decode → AES/CBC 解密 → UTF-8 字符串；加密方法执行 AES/CBC 加密 → Base64.encodeToString。

该实现使用固定 IV。n 类的 AES 包装中没有看到 HMAC、认证标签或其他密文完整性校验。因而应将它描述为客户端 payload 加密，而不是带认证的 AEAD 方案。HTTPS 是另一个独立传输层，不能把两者混为一谈。

## 2. AES 的实际消费者与网络路径

### 2.1 GNSS 导航电文上报：locnu

静态调用链：

1. z 类的 Handler 收到 GnssNavigationMessage 消息后，将导航电文交给 x 类。
2. s 类按导航消息 type 与 SVID 建立分组，记录 submessageId 和 getData() 返回的原始字节；部分数据转成二进制位串，部分数据按字节转成逗号分隔的有符号整数串。
3. s 类在数据组完整时生成以 GPS 时间和导航电文内容组成的记录。
4. x 类在最近一次导航消息时间窗口内、且队列非空时拼接待发送数据。
5. x 类分别调用 n.b().b(...) 对 info 和 enl 加密，随后将其 URL 编码并放入 POST 参数。
6. 请求目标为 https://ofloc.map.baidu.com/locnu。

字段含义：

| 字段 | 加密前内容 | 处理 |
|---|---|---|
| info | Baidu SDK 身份/设备信息，并附加 gnsst 时间值 | AES-CBC 后 Base64 |
| enl | s 类组装的 GNSS 导航电文记录 | AES-CBC 后 Base64 |

这里的 GNSS 数据是 Android GnssNavigationMessage API 提供的导航电文，不应误称为已经证明上传了原始 GNSS 测量值或完整设备定位历史。该路径存在明确的原始导航消息采集与加密请求构造，但回调是否在目标 ROM 中注册、请求是否实际发出、服务器是否接收，均未在本轮动态验证。

### 2.2 定位结果接口：enc=2 与响应解密

m$c.smali 显示：

- 构造请求时，如果 n 单例成功取得 AES 参数，就在请求内容末尾追加 &enc=2。
- 随后请求主体中的 bloc 字段由 Jni.f(...) 处理。Jni.f 对应 native ee 路径，另加 tp=4；它不是 n.java 的 AES 方法。
- 收到响应后，处理器检查响应是否包含 enc；如果 JSON 存在 enc 字段且 AES 参数可用，就调用 n.a(enc) 解密，再继续解析定位结果及相关字段。

请求的默认通用 endpoint 为 https://loc.map.baidu.com/sdk.php。网络基类使用 HTTPS POST、application/x-www-form-urlencoded，并支持 gzip 响应。

### 2.3 Wi-Fi 热点识别接口：历史数据进入请求

l.java / l$a.smali 显示：

- l 类在 Wi-Fi 已连接、可取得 BSSID 的情况下查询本地 hstdata。
- 如果 BSSID 未命中本地缓存，或缓存时间超过 259200 秒（3 天），会构造热点识别请求。
- 请求内容包括当前蜂窝/Wi-Fi 相关信息、设备/SDK 信息，并在 l.a(boolean) 中追加 f.c().a() 返回的历史字段。
- 当 AES 参数可用时，请求内容追加 &enc=2；真正放入 bloc 的请求内容仍通过 Jni.f(...) 处理。
- 响应处理器在 JSON 有 enc 字段时调用 n.a(enc) 解密，再解析 content.imo 中的 mac 与 mv，更新本地 hstdata。

因此，AES 参数至少有两种明确用途：GNSS locnu 请求的出站字段加密，以及定位/热点接口响应 enc 字段的解密。不能仅凭 &enc=2 就说整个 bloc 请求体使用了 AES。

## 3. cl_pre / wf_pre / ll_pre 历史记录

### 3.1 存储位置与编码

- r.java 的 a(Context) 返回名为 MapCoreServicePregck 的 SharedPreferences。
- f.java 从该 SharedPreferences 读取 cl_pre、wf_pre、ll_pre。
- 默认 h=1、i=1；两类队列上限均为 5 条。
- 存储时将记录串以竖线分隔，再进行 Base64.encode；读取时 Base64.decode 后重新拆分。
- Base64 是编码，不是加密；本路径没有调用 n 类 AES。

### 3.2 记录字段

| 队列 | 静态代码可确认的内容 | 处理方式 |
|---|---|---|
| cl_pre | 经度、纬度、时间 | 首条绝对值，后续经纬度/时间差分 |
| wf_pre | 经度、纬度、时间 | 首条绝对值，后续经纬度/时间差分 |
| ll_pre | cVar.A()、半径、海拔、时间、速度、Location 经度、Location 纬度 | 首条绝对值，后续字段差分；经纬度差乘 10^6 |

cl_pre / wf_pre 的坐标取自 cVar.t() 与 cVar.q()；Baidu Location 对象的 toString 中分别将 q()、t() 显示为 lat、lon。ll_pre 的第一列来自 cVar.A()，本报告保留原始 getter 名称，不擅自赋予未证实的语义。

### 3.3 发送路径与触发条件

f.c().a() 生成 &ll_pre、&cl_pre、&wf_pre 参数。当前已确认的消费者是 l.a(boolean) 构造的 Wi-Fi 热点识别请求，而不是“所有定位请求都会无条件带上这三组字段”。

特别注意：f.java 的分支中，cl_pre 有来源标记和开关条件；ll_pre 只在定位类型/开关/Location 条件满足时写入；wf_pre 的写入代码位于前面分支之后。报告保留这一真实控制流，不用队列名称推断其一定只代表 Wi-Fi 定位。

## 4. intime.dat：位置轨迹文件与上传

### 4.1 触发与配置

j.java 中可见的默认配置：

| 字段 | 默认值 | 代码中的用途 |
|---|---:|---|
| on | 1 | 总开关 f36a |
| bash | 0.7 | 与电量百分比比较的阈值 f37b |
| net | 3G\|4G | 允许的网络类型 f38c |
| tcon | 1 | 运动/上传控制分支 d |
| tcsh | 307200 | 计数阈值 e |
| per | 15 | 轨迹封存周期 f，单位秒 |
| spsh | 3.5 | 速度阈值 g |
| acsh | 3.0 | 加速度相关阈值 h |
| stspsh | 0.5 | 低速阈值 i |
| drstsh | 300 | 停留相关阈值 j |
| stper | 60 | 时间参数 k |
| nondron | 0 | 标志 l |
| nondrper | 60 | 时间参数 m |

e(Location) 的门控逻辑要求 on=1、电量百分比小于 bash×100，并且配置 net 字符串包含当前网络类型。当前网络类型由 g.b.a(int) 映射为 WIFI/2G/3G/4G/unknown。默认 net 为 3G|4G，因此默认配置不匹配 WIFI。默认 bash=0.7 对应电量低于 70% 的比较条件。另有 tcon 与本地计数阈值检查。

这些值是 Java 字段默认值；远端 cc.php 配置响应可以通过 on、bash、net、tcon、tcsh、per、spsh、acsh、stspsh、drstsh、stper、nondron、nondrper、uptime 等字段覆盖它们。本轮没有向 cc.php 请求配置，因此远端当前值 UNKNOWN。

### 4.2 轨迹记录格式

j.java 将 Location 对象转换为 byte 列表：

- 首个点写入 Location 时间（秒）、经度×10^6、纬度×10^6，各为 32 位小端整数。
- 首点还写入方向和速度压缩值：方向按 15 度量化；速度先换算为 km/h，再按 4 km/h 单位量化。
- 后续点写入经度/纬度差值的低、高字节，并在方向字段中编码坐标差的符号；另写方向与速度字段。
- 文件头含总长度、记录数、版本字节 9.5.2.1、标记字节以及应用/设备身份串。
- 身份串由 packageName + ":" + CUID 组成；代码对每个字节 XOR 一个 SecureRandom 生成的随机字节，并把该随机字节及另一个随机字节附加到结果。该操作属于可逆 XOR 混淆，不是 AES。

一个重要未决点：d(Location) 中存在 now - x < w 的 500ms 判断，w 默认 500，但在 j.java 本类中未找到 x 的赋值。外部写入尚未完全排除，因此本报告不将“有效采样间隔为 500ms”写成结论。封存周期 per=15 秒则有明确的 A 时间戳判断。

### 4.3 文件写入、上传与失败处理

- 文件路径：由 i.i.d() 返回的目录下的 baidu/tempdata/intime.dat。
- 每次生成新文件前，如果同名文件存在会先删除，再写入新的二进制内容。
- 上传线程向 https://itsdata.map.baidu.com/long-conn-gps/sdk.php 发起 HTTPS POST。
- multipart 字段名为 location_dat，文件名为 intime.dat，内容类型为 application/octet-stream。
- 连接与读取超时均为 10 秒；上传函数逐块读取文件并写入请求体。
- 收到 HTTP 响应码后，代码将本地计数器 n 增加 400 并写入 grtcf.dat；只有响应码 200 时返回成功标记。
- 上传函数本身没有在响应后删除 intime.dat；下次生成新文件时才删除同名旧文件。未见明确的失败重试队列或持久化待发送队列。异步上传与下次覆盖之间是否存在竞争，需要动态验证，当前标记为 UNKNOWN。
- a(String, Context) 在当前反编译结果中直接返回 true；因此此处未见一般性的包名白名单限制。Uber Driver 包名另走文件锁分支。

### 4.4 TLS 验证实现

intime.dat 上传前调用 HttpsURLConnection.setDefaultSSLSocketFactory(i.i.g())，并为当前连接设置 HostnameVerifier。

i.i.g() 创建的 X509TrustManager：
- checkClientTrusted 为空实现；
- checkServerTrusted 只对证书调用 checkValidity()；
- getAcceptedIssuers() 返回空数组。

j.java 的 HostnameVerifier 则要求 URL host 与传入 hostname 完全相等。因此这里有主机名比较，但没有看到正常的 CA 信任链验证或证书 pinning。setDefaultSSLSocketFactory 是设置进程默认工厂的静态调用，可能影响之后创建的 HTTPS 连接；具体影响范围需要运行时验证。

这说明当前上传路径的 TLS 证书验证弱于标准 PKI 校验，不等于已经发生 MITM，也不证明任何真实数据被第三方截获。

## 5. 已确认与仍未知

### 已由当前样本静态证据确认（E1）

- ARM64 liblocSDK8b.so 中存在可还原的固定 AES key/IV 字符串。
- n.java 使用 AES/CBC/PKCS5PADDING 和 Base64 完成加解密。
- x.java 对 info/enl 调用 AES 加密并将请求指向 locnu。
- l/m 的请求构造会附加 enc=2；响应处理器会按 enc 字段尝试 AES 解密。
- GNSS 导航消息存在采集、分组、组装和 locnu 请求构造路径。
- cl_pre/wf_pre/ll_pre 的 SharedPreferences 存储、Base64/差分编码及热点识别请求消费者。
- intime.dat 的轨迹字段、文件写入、multipart 上传调用和 TLS TrustManager 实现。

### 本轮没有证明（UNKNOWN / NOT_RUN）

- 目标 ROM 是否实际注册并触发 GnssNavigationMessage 回调。
- 任何一条请求在真实设备上是否真正发出。
- 生产服务器是否收到、解密、持久化或进一步使用数据。
- 服务器当前返回的 cc.php 配置值及其变化历史。
- intime.dat 在具体设备上的实际文件字节、文件生成频率和真实上传频率。
- 上传失败后是否存在服务端或其他组件层面的补偿机制。
- j.java 的 x 字段是否由外部反射/其他代码写入。
- 其他 ABI 是否使用同一组 AES 常量。
- 真实设备上的证书链验证结果和实际 TLS 握手行为。
