# SystemHelper 深入逆向复核（2026-11-10）

> 范围：用户提供的 SystemHelper.apk，SHA-256 `38a9010600bc91fd468701f53ba37ea0d43cb8e906544d0700a799f592011428`。
> **威胁模型**：预装、高系统权限、相关权限均可用；但代码中的国家/运营商/联网/用户选项条件仍需按实际分支理解，不能凭权限假设跳过。
> 证据为 Java 反编译与 Dalvik Smali/指令互证；原生 JNI 与真实机运行行为尚未全量恢复。

## 1. 代码还原与完成度

- 完整输入：4,107,356 字节原版 APK、ZIP 内容、DEX、资源和两个 ARM64 SO。
- DEX：1,149 类定义、8,767 已定义方法、8,308 带代码方法、86,395 条类型/字段/调用/字符串引用。
- **结构级恢复**：Apktool 3.0.3 输出 1,149 个 Smali；同时保留原 DEX 与 1,004 个按类文件拆出的 Dalvik 指令记录，主要差异是无方法体的类没有对应 Dalvik 指令文件。
- **高层 Java**：JADX 常规模式 585 个 Java 文件，报告 6 个反编译错误（exit=3）；fallback 模式 586 个 Java 文件（exit=0）。一个 Java 文件可包含多个类或内部类，不能按文件数误算类覆盖率。遇到 `throw th`、`UnsupportedOperationException("Method not decompiled")` 等必须回查 Smali。
- **ARM64**：`liblocSDK8b.so` 与 `libindoor.so` 均已有整库 AArch64 objdump 反汇编、readelf 和 strings；但未做所有 JNI 函数的语义/动态依赖验证。
- **运行态**：尚无设备权限、真实日志、真实 HTTP POST 的实验记录，不可称功能行为 100% 已验证。

## 2. 能力模块的启动链

`DMApplication.onCreate()` / `OnBootReceiver.onReceive()` -> `AlarmHelper` 的五个独立 PendingIntent 唤醒器 -> `ScheduleRegisterReceiver`、`AppInfoRegisterReceiver`、`SignalInfoRegisterReceiver`、`GetSignalInfoReceiver` 等 -> `DeviceManager` (`c.d.a.a.n`) -> 设备/位置/应用数据模型 -> `RegisterThread` (`control.g`) -> HTTP 连接或本地待发队列。

源文件：[OnBootReceiver](../decompiled/jadx/sources/com/mobiletools/systemhelper/control/OnBootReceiver.java)、[AlarmHelper](../decompiled/jadx/sources/c/d/a/b/a.java)、[DeviceManager](../decompiled/jadx/sources/c/d/a/a/n.java)、[上传线程](../decompiled/jadx/sources/com/mobiletools/systemhelper/control/g.java)。

| 类型 | 精确默认配置 | 含义 |
|---|---|---|
| 开机后首轮入口 | 240,000 ms | 定时显式广播 `OnBootReceiver`，与主开机广播不同 |
| 常规注册 | 86,400,000 ms | 24 小时 |
| 应用注册 | 86,400,000 ms | 24 小时 |
| 信号上传 | 43,200,000 ms | 12 小时 |
| 信号获取 | 1,800,000 ms | 30 分钟 |
| 首轮随机延迟 | 每项 `Random.nextInt(86400000)` | 随机 0–24 小时，取决于首次和进程内计数器 |
| SIM 就绪延时 | **180,000 ms** | **实际 3 分钟**。日志硬编码为“wait ... 6 minutes”，日志与代码不一致 |

以上是设定值；唤醒是否真正执行仍受设备耗电优化、广播分发、时间调整和设置变化影响。导出管理 Binder 可以修改 SharedPreferences 中的七个间隔字段；部分首次默认随机值是进程生命周期中的静态值。

## 3. 真实上报集合的精确范围

**设备注册**：[DeviceInfo](../decompiled/jadx/sources/com/mobiletools/systemhelper/control/b.java) 将机型、系统版本、IMEI、IMSI、ICCID、双卡、MNC、CID/TAC/PCI、5G/VoLTE/VoNR 等字段组合为 JSON；针对 Vivo 使用隐藏 `vivoTelephonyApi`，故不是单纯基于一般 Android SDK。

**应用信息**：[control.f](../decompiled/jadx/sources/com/mobiletools/systemhelper/control/f.java)：

1. `getInstalledApplications(0)` 读取应用元数据集合，用于匹配包名、UID 和展示名称。
2. `queryAndAggregateUsageStats(now - 86400000, now)` 取得最近 24 小时 UsageStats，对返回的记录按前台总使用时长排序。
3. 对每个 UsageStats 包名匹配应用 UID，并通过 `NetworkStatsManager.querySummary` 读取按 UID 归属的 SIM1、SIM2、Wi-Fi 收发流量。SIM 流量换算除以 1,024（KiB），Wi-Fi 流量除以 1,048,576（MiB）；字段单位并不统一。
4. [DeviceManager 回调](../decompiled/jadx/sources/c/d/a/a/n.java) 过滤 `pkgName.startsWith("com.android")` 的条目，其余进入 `AppInfo` JSON。

因此：**存在完整安装信息读取能力，但这一条上报链的实际集合以使用记录为索引，不能声称该链自动上传全部已安装应用**。另外统计按 UID 归属，系统共享 UID 场景可能混淆多个包的数据归属。应用采集查询时间窗由静态 `d.t=86400000` 定义，**不是**由可修改的闹钟调度间隔直接控制。

**信号与位置**：[GetSignalInfoReceiver](../decompiled/jadx/sources/com/mobiletools/systemhelper/control/GetSignalInfoReceiver.java) 启动 Baidu 定位，配置高精度模式；回调将经纬度、海拔和对应 SIM 的 LTE/NR 信号数据组成 JSON。只在对应 MNC 值以 `460` 开头等条件满足时缓存。它的范围包括基站标识与方向/速度而不只是经纬度。

## 4. 缓存与补发的真实语义（新增可靠性问题）

[SignalDatabaseHelper](../decompiled/jadx/sources/c/d/a/b/m.java) 将位置信号 JSON 保存到 `signalhelper` 数据库 `signal` 表，插入时若记录数已达到 100，删除查询到的最前一条；`DeviceManager` 的 `RegType=R` 分支**先取得全部信号 JSON，再调用 `clearSignalDB()`，之后才安排上传线程**。

[HistoryDatabaseHelper](../decompiled/jadx/sources/c/d/a/b/e.java) 使用 `systemhelper` 数据库 `dmregister` 表，保留约 10–11 条历史记录（插入前按照现有数量裁剪）。`a():JSONObject` 以**未显式排序的**查询 `moveToLast()` 取得一条记录，**立即 DELETE**，然后才返回 JSON。[HistoryPostThread](../decompiled/jadx/sources/com/mobiletools/systemhelper/control/e.java) 发送一次，收到失败结果只是记录日志，不会恢复被删除的数据。

**结果**：断网/服务器错误/进程崩溃可能造成“先删除、后发送失败”的不可恢复数据丢失，且无法保证按队列创建时间顺序重试。并不能简单声称这里实现了可靠的离线补发。

[RegisterThread](../decompiled/jadx/sources/com/mobiletools/systemhelper/control/g.java) 在当前条件允许并且直接上传成功时启动一次 `HistoryPostThread`；并没有循环完整历史队列。

## 5. 传输协议及身份鉴别问题（新增）

[CipherHelper](../decompiled/jadx/sources/c/d/a/b/c.java) 对**完整明文 JSON** 计算 MD5；这 16 字节直接作为 AES-128 密钥，正文使用 `AES/ECB/PKCS5Padding`。它另将 MD5 字节通过 [RSAHelper](../decompiled/jadx/sources/c/d/a/b/j.java) 使用内置 `assets/pub.cer` 中的 **公开 RSA 公钥**执行 `Cipher.ENCRYPT_MODE`，Base64/URL encode 后作为 URL 的 `sign=` 参数。

因此 `sign` 不是用客户端私钥生成的数字签名；任何获取公开证书的人都能对自己构造的摘要执行同样的公钥加密。这种客户端封装**自身无法提供发送方真实性证明**，除非服务端另外进行独立的设备鉴权或白名单检查（未审）。

[RegisterThread](../decompiled/jadx/sources/com/mobiletools/systemhelper/control/g.java) 的目标路径含 `?ver=5.0&model=...&manuf=...&sign=...`；**机型与制造商直接出现在 URL 查询字符串，默认 HTTP 可观察**。请求体经过应用层 AES 加密，所以不能称为“HTTP 中直接上传明文 JSON”。服务端 HTTP 200 算成功，注册线程将 **416 也视作成功**。这意味着后续历史队列是否被重试可能依赖服务端响应码，而非严格 2xx。

AES/ECB 不提供认证加密，不应假定密文防篡改。RSA 1024 位密钥过短；MD5 摘要与业务数据同源，不是随机会话密钥。

## 6. Binder 可达能力与边界

[Manifest](../decoded/AndroidManifest.xml) 中 `RegisterHelperService` 导出且没有绑定签名级权限。其 [Binder](../decompiled/jadx/sources/com/mobiletools/systemhelper/service/a.java) 事务为：

| 事务 | 调用 | 配置效果 |
|---|---|---|
| 1 | `a(String)` | 修改 `serverAddress` |
| 2 | `a(int)` | 修改 7 组定时配置 |
| 3 | `b()` | 删除 SharedPreferences 配置文件 |
| 4 | `a(boolean)` | 开关 Logcat 日志 |
| 5 | `a()` | 查询日志状态 |

[服务实现](../decompiled/jadx/sources/com/mobiletools/systemhelper/service/RegisterHelperService.java) 的 `onBind` 不检查调用方 UID；`onTransact` 的 `enforceInterface` 只检查接口描述令牌，不是 Android 系统权限鉴权。

在普通应用获准绑定这一 exported 服务的前提下，可未经身份校验地修改上报目的地（密文不因此自动解密）、触发明文采集日志和影响调度周期。这是**高优先级的本地 IPC 权限边界问题**。没有真机绑定验证、也没有远程攻击链结论。

## 7. 定位 SDK / 原生库与关键欠账

- 百度 SDK 注册了 `:remote` 服务；Java host `GetSignalInfoReceiver` 会主动调用定位 client。
- `liblocSDK8b.so` 368,568 字节；`libindoor.so` 1,596,896 字节。两者有 AArch64 整库反汇编与 JNI 导出符号，但不等于所有 native 算法均已逆向理解。
- `libindoor.so` 还需要 `libapp_BaiduVIlib.so`、`libmml_framework.so`；这两份文件不包含在提供的 APK 中。是否由设备其它位置提供未核实。
- 与后台及系统事件有关的其他逻辑包括 `TelephonyCallback` 的精细数据连接失败原因/通话断开原因监听；部分监听注册时机并不直接等价于用户授权时机。
- `TestActivity` 也导出，执行设备信息读取和本地 UI 展示；未找到仅凭其 intent 就直接跨进程返回敏感 JSON 的机制。

## 8. 当前明确不能判定的事实

1. 服务端是否实际接收、如何存储和保留数据；上传的每个 JSON 在真实设备上是否完整形成。
2. 被导出服务在**指定手机固件**上的绑定结果、Android SELinux/AppOps 限制，以及真实身份验证防护。
3. 百度定位 SDK 的所有分支和两份 SO 原生函数的动态路径、真正联网域名及传输内容。
4. APK 代码之外的系统固件配置、其它同 UID 应用、厂商业务协议及数据治理事实。
5. JADX 的六处高层反编译错误对应的完整语义；必要时应以 Apktool Smali 复核。

因此：**代码结构已经全量保存，可读源码与主要业务链已恢复，但“完全理解所有执行路径”尚未完成**。本文件是阶段审计，不是全面行为验收的替代品。

## 9. 人工复核后的高层反编译缺口

[自动检查清单](verification/jadx-method-gaps.md) 在常规 JADX Java 输出中找到 **12 处 `Method not decompiled` 方法占位**及 3 处 `JADX ERROR` 注释（共 15 个标记），不能把“JADX CLI 报告 6 errors”直接等同于“仅 6 个 Java 方法有缺陷”。所有普通模式文件都有同相对路径 fallback，且都可回查 Smali。

宿主 `com.mobiletools.systemhelper` 内只发现一个完整方法占位：`control/SIMStateReceiver.onReceive`。它在 [fallback 版](../decompiled/jadx-fallback/sources/com/mobiletools/systemhelper/control/SIMStateReceiver.java) 和 [原始 Dalvik 记录](../disassembly/com__mobiletools__systemhelper__control__SIMStateReceiver.dalvik.txt) 中仍保有完整指令，正是我们复核 SIM 状态及 **180,000 ms** 延时的依据。其余高层未还原方法主要位于混淆第三方代码及 Android support/Constraint 库。

## 10. 原生 JNI 静态清单与依赖约束

| ARM64 库 | 文件大小 | `Java_com_*` 导出符号 | 观察到的主要类别 |
|---|---:|---:|---|
| `liblocSDK8b.so` | 368,568 字节 | 18 | 百度定位数据编码/加密、Murmur 摘要、位置 JNI |

## 11. 再补充的资源管理风险

[HistoryDatabaseHelper.a()](../decompiled/jadx/sources/c/d/a/b/e.java) 在找到记录并成功构造 JSON 的路径中，`return new JSONObject(string)` **发生在 Cursor/CursorWindow.close() 之前**。结合该方法先行删除数据的行为，反复历史补发可能带来 Cursor/窗口资源泄漏。这个问题属于本地资源可靠性，不是已观察到的真实崩溃。
